Guía completa y visual del backend — desde el VPS hasta el navegador

🐍 Django 🐳 Docker ⚡ WebSockets 🔴 Redis 🐘 PostgreSQL 🌐 Nginx 🔔 Notificaciones RT
📖 Introducción — Por qué importa entender esto

Este documento te explica cómo está construido el backend de TallerPro desde cero. No asume que ya sabes de infraestructura — va a explicar cada pieza como si fuera la primera vez que la ves.

💡

La idea clave: El backend no es un solo programa. Es un conjunto de servicios especializados que trabajan juntos. Nginx maneja el tráfico, Gunicorn sirve la API, Daphne sirve los WebSockets, Redis manda mensajes internos, PostgreSQL guarda los datos. Docker los mantiene a todos corriendo sin que se pisen entre sí.

Cuando entiendes esto, dejas de ver el backend como una caja negra y puedes:

  • Saber exactamente a dónde ir cuando algo falla
  • Leer los logs del contenedor correcto
  • Entender por qué un cambio en settings/production.py afecta todo
  • Configurar nuevas features sin romper lo que ya funciona
  • Hablar con cualquier dev de backend y entender qué te están diciendo
🏢 La Analogía del Edificio

Imagina que el backend es un edificio de oficinas moderno. Así funciona cada pieza:

🚪 Nginx = La Recepción

Es lo primero que ves al llegar. Recibe a todos, lee a dónde quieren ir (/api/, /ws/, /static/) y los manda al piso correcto. No hace el trabajo él solo — solo dirige el tráfico.

🏭 Gunicorn = Fábrica de Respuestas HTTP

Es el departamento principal. Cuando alguien pide datos de clientes, citas o inventario, aquí Django procesa la petición y regresa el JSON. Llega petición → procesa → responde → cierra conexión.

📞 Daphne = Centralita Telefónica

Mantiene líneas abiertas con cada usuario conectado. Cuando pasa algo importante (nueva cita, orden lista), la centralita les avisa inmediatamente sin que ellos tengan que preguntar.

🗂️ PostgreSQL = El Archivo Central

Sótano del edificio. Aquí vive toda la información: clientes, vehículos, citas, órdenes de trabajo. Nadie accede al archivo directamente — siempre hay un empleado (Django) que va a buscarlo.

📣 Redis = El Intercomunicador

Los altavoces internos del edificio. Cuando Gunicorn quiere avisarle algo a Daphne — "llegó una nueva cita, avísale al usuario" — le manda un mensaje por los altavoces. Redis entrega el mensaje al instante.

🐳 Docker = Las Paredes

Cada departamento está en su propio cuarto sellado (contenedor). Si uno se rompe, los demás siguen funcionando. Docker asegura que cada cuarto tenga exactamente lo que necesita para operar.

🐳 Docker — Los Contenedores y Cómo Se Hablan

Docker permite correr programas en contenedores aislados. Piénsalo como una computadora virtual muy ligera — tiene su propio sistema de archivos, sus propias variables de entorno, su propio proceso, pero comparte el kernel del sistema operativo del VPS.

¿Por qué usamos Docker en TallerPro?

  • Reproducibilidad: El entorno local es idéntico al del VPS. "En mi máquina funciona" deja de ser un problema.
  • Aislamiento: Si Postgres falla, Django sigue corriendo. Si WAHA se cuelga, la API no se cae.
  • Facilidad de deploy: Un solo comando docker compose up --build -d levanta todo.

Cómo se comunican los contenedores entre sí

Docker crea una red virtual interna llamada taller_network. Dentro de esa red, cada contenedor tiene un hostname que es su nombre de servicio. Entonces:

  • Django se conecta a Postgres como db:5432 (variable DB_HOST=db)
  • Django se conecta a Redis como redis:6379 (variable REDIS_HOST=redis)
  • WAHA le manda webhooks a Django como http://web:8000/api/webhooks/whatsapp/
  • Nginx del sistema habla con los contenedores via localhost:8001 y localhost:8002

Los dos docker-compose

docker-compose.local.yml — Desarrollo

Para tu computadora. Sin SSL. Incluye Nginx como contenedor. Django usa settings/development.py. El código se monta como volumen — los cambios se reflejan sin rebuild.

docker compose -f docker-compose.local.yml up --build

docker-compose.yml — Producción

Para el VPS. Sin Nginx en Docker (está en el sistema). El código está bakeado en la imagen. Debes hacer --build para que los cambios de código surtan efecto.

docker compose up --build -d
🚫

Error común: Hacer docker compose restart después de cambiar código en producción NO funciona. El restart reinicia el contenedor pero con la imagen vieja. Siempre necesitas --build para reconstruir la imagen con el nuevo código.

🌐 Nginx — El Portero Inteligente

Nginx es un servidor web y reverse proxy. En TallerPro cumple tres funciones:

  • Reverse proxy: recibe peticiones de internet y las reenvía al servicio correcto
  • Servidor de archivos estáticos: sirve CSS, JS, imágenes directamente desde disco sin pasar por Django
  • Terminador SSL: desencripta HTTPS y habla con Django por HTTP interno

¿Qué significa "reverse proxy"?

El cliente nunca habla directamente con Django. Habla con Nginx, Nginx le pregunta a Django, y le regresa la respuesta al cliente. Django nunca ve el internet directamente — Nginx lo protege.

Cómo Nginx enruta cada petición (tu archivo real del VPS)

/static/→📁 /var/lib/docker/volumes/taller_static/_data/Sin Django
/media/→📁 /var/lib/docker/volumes/taller_media/_data/Sin Django
/ws/→⚡ localhost:8002 (Daphne)Con headers Upgrade
/→⚙️ localhost:8001 (Gunicorn/Django)Todo lo demás

El truco de los WebSockets en Nginx

HTTP normal es como mandar una carta: envías, recibes respuesta, se acabó. WebSocket es como una llamada telefónica: la conexión queda abierta. Para que Nginx convierta una petición HTTP en WebSocket necesita dos headers especiales:

# Sin estos dos headers, los WebSockets NO funcionan
proxy_set_header Upgrade $http_upgrade;   # Le dice: "este es un upgrade de protocolo"
proxy_set_header Connection "upgrade";    # Confirma el upgrade
proxy_http_version 1.1;                  # WebSocket requiere HTTP/1.1

Tu archivo /etc/nginx/conf.d/taller-pro.conf ya tiene esto correctamente configurado en el bloque location /ws/.

SSL — cómo funciona HTTPS

Servidor HTTP (:80)

Solo acepta el challenge de Let's Encrypt (para renovar certificados) y redirige todo a HTTPS con return 301.

Servidor HTTPS (:443)

Lee el certificado de /etc/letsencrypt/live/api.autotronia.com/, desencripta las peticiones, y las manda a Django por HTTP interno (localhost:8001).

⚙️ Gunicorn vs Daphne — Dos Servidores, Dos Propósitos

⚙️ Gunicorn — Servidor WSGI

WSGI = Web Server Gateway Interface. Estándar clásico de Python para web.

Cómo funciona: Llega petición HTTP → Django procesa → regresa respuesta → conexión cerrada. Sincrónico y stateless.

Para qué: Toda la API REST (/api/customers/, /api/workshop/, etc.) y el admin.

Archivo de entrada: config/wsgi.py

Puerto en host (producción): 8001

⚡ Daphne — Servidor ASGI

ASGI = Asynchronous Server Gateway Interface. Estándar moderno que soporta conexiones persistentes.

Cómo funciona: El cliente conecta → la conexión queda ABIERTA → el servidor puede mandar mensajes cuando quiera.

Para qué: Las notificaciones en tiempo real (/ws/notifications/).

Archivo de entrada: config/asgi.py

Puerto en host (producción): 8002

📋 models.py — Las Tablas

Define la estructura de la base de datos. Cada clase Python es una tabla en PostgreSQL. Cada atributo es una columna.

class Customer(models.Model):
    name = models.CharField(max_length=200)
    email = models.EmailField()
    tenant = models.ForeignKey('Tenant'...)

🔄 serializers.py — El Traductor

Convierte objetos Python en JSON (para el frontend) y JSON en Python (para guardar en BD). También valida los datos entrantes.

👁️ views.py — Los Manejadores

Recibe las peticiones HTTP, llama al servicio correspondiente, y regresa la respuesta. Es como el mesero: toma el pedido, lo manda a la cocina, trae el plato.

🗺️ urls.py — Las Rutas

Conecta URLs con vistas. Define el "menú" de endpoints disponibles en esta app.

path('customers/', CustomerListView),
path('customers/<id>/', CustomerDetailView),

🧠 services/ — La Lógica de Negocio

El cerebro. No sabe nada de HTTP ni JSON — solo sabe de reglas: "Para crear una cita, verifica que el mecánico esté disponible, calcula la duración, envía notificación." Se puede reusar desde signals, otras vistas, etc.

🗄️ repositories/ — Las Consultas

Centraliza todos los Customer.objects.filter(). Separa la lógica de base de datos de la lógica de negocio.

⚡ signals.py — Eventos Automáticos

Como triggers de base de datos pero en Python. "Cuando se cree una cita (post_save), automáticamente ejecuta este código." Así es como una cita nueva genera una notificación automáticamente.

📜 migrations/ — El Historial de la BD

Cada cambio en models.py genera un archivo de migración. Son como "commits" de la base de datos — un historial de todos los cambios al esquema.

python manage.py makemigrations
python manage.py migrate

🧱 Middleware — Las Capas de Seguridad

El middleware es una cadena de filtros que procesa cada petición antes de que llegue a tu vista. Como los controles de seguridad en un aeropuerto: hay diferentes puestos que revisan distintas cosas en orden.

1
SecurityMiddleware

Agrega headers de seguridad HTTP. En producción fuerza HTTPS.

2
SessionMiddleware

Maneja sesiones de usuario (para el admin de Django, que usa sesiones, no tokens).

3
CorsMiddleware Crítico

Revisa si el origen de la petición está en CORS_ALLOWED_ORIGINS. Si viene de app.autotronia.com ✅ la deja pasar. Si viene de otro dominio no autorizado, regresa 403. Debe estar antes de CommonMiddleware.

4
CommonMiddleware

Normalización de URLs (agrega trailing slash, etc.).

5
AuthenticationMiddleware Crítico

Lee el header Authorization: Token xxxxx, busca el token en BD, y adjunta el usuario a request.user. Después de esto, el código sabe quién está haciendo la petición.

6
TenantMiddleware Custom

Lee el header X-Tenant-Id y adjunta el tenant a request.tenant. Así las vistas saben a qué taller pertenece esta petición.

7
TenantFromUserMiddleware Custom

Si el header no vino pero el usuario está autenticado, infiere el tenant desde el usuario. Fallback del anterior.

✓
→ Tu Vista recibe la petición

Con request.user (quién eres) y request.tenant (a qué taller perteneces) ya resueltos.

⚡ WebSockets — La Línea Directa en Tiempo Real

¿Qué es un WebSocket?

HTTP tradicional es como mandar un email: tú preguntas, el servidor responde, se acabó. Para saber si llegó algo nuevo, tienes que preguntar de nuevo (y de nuevo...). WebSocket es como una llamada telefónica: una vez establecida la conexión, ambos lados pueden hablar cuando quieran.

✅

En TallerPro: Cuando un mecánico termina una orden de trabajo, la notificación llega al admin en el navegador al instante, sin que el admin tenga que recargar la página.

Los archivos involucrados

ArchivoRol
config/asgi.pyEl portero ASGI. Valida el origen, aplica autenticación, enruta al Consumer correcto.
apps/core/routing.pyDefine qué URL de WebSocket corresponde a qué Consumer. Como urls.py pero para WS.
apps/notifications/consumers.pyEl handler del WebSocket. Maneja conexión, desconexión y mensajes.
apps/notifications/services.pyLa función que otros módulos llaman para enviar una notificación via Redis.
config/settings/base.pyCHANNEL_LAYERS: configura Redis como bus de mensajes entre Gunicorn y Daphne.

El asgi.py explicado

# config/asgi.py
application = ProtocolTypeRouter({
    # Peticiones HTTP → Django normal (mismo que Gunicorn)
    "http": django_asgi_app,

    # Peticiones WebSocket → esta cadena de validaciones
    "websocket": CorsOriginValidator(   # 1. ¿El origen está en CORS_ALLOWED_ORIGINS?
        AuthMiddlewareStack(             # 2. Aplica autenticación Django
            URLRouter(websocket_urlpatterns) # 3. Enruta a NotificationConsumer
        )
    ),
})
💡

¿Por qué CorsOriginValidator y no AllowedHostsOriginValidator? El validador original revisaba el Origin del WebSocket contra ALLOWED_HOSTS (que solo tiene api.autotronia.com). Pero el frontend manda Origin: https://app.autotronia.com, que es un dominio diferente, así que lo rechazaba. El custom validator revisa contra CORS_ALLOWED_ORIGINS que sí incluye el dominio del frontend.

Autenticación en WebSockets

Los WebSockets no pueden mandar headers HTTP custom. Por eso el token va en el query string de la URL:

# URL del WebSocket desde el frontend
wss://api.autotronia.com/ws/notifications/?token=abc123xyz

# El Consumer lo lee así en connect():
query_string = self.scope['query_string'].decode()  # "token=abc123xyz"
token_key = ...  # extrae "abc123xyz"
token = Token.objects.get(key=token_key)           # busca en BD
self.user = token.user                              # ¡ya tiene el usuario!

Channel Groups — grupos de usuarios

Grupo personal: user_42

Solo este usuario está en este grupo. Las notificaciones personales se envían aquí.

Grupo del tenant: tenant_1

Todos los usuarios del mismo taller. Los broadcasts generales llegan a todos simultáneamente.

🔴 Redis — El Mensajero Interno

Redis es una base de datos en memoria (RAM) extremadamente rápida. En TallerPro su rol principal es ser el bus de mensajes entre Gunicorn y Daphne.

💡

El problema que resuelve: Gunicorn y Daphne son procesos completamente separados. Si Gunicorn quiere avisar a Daphne "hay una notificación para el usuario 5", ¿cómo lo hace? No pueden hablar directamente — están en procesos diferentes. La respuesta es Redis: Gunicorn escribe en Redis, Daphne lo lee, Daphne lo manda al WebSocket.

# Cómo se envía una notificación (apps/notifications/services.py)
channel_layer = get_channel_layer()

await channel_layer.group_send(
    f"user_{user_id}",           # ¿A qué grupo de Redis?
    {
        'type': 'notification_message',  # Método del Consumer a ejecutar
        'notification': {...}              # Los datos
    }
)
# Redis lo entrega a Daphne → Daphne lo manda por el WebSocket abierto
🏪 Multi-Tenant — Un Backend, Múltiples Talleres

TallerPro puede servir a múltiples talleres simultáneamente con un solo backend. Cada taller es un "tenant". La información de un taller nunca se mezcla con la de otro.

# Sin multi-tenant (peligroso — ve datos de todos):
Customer.objects.all()

# Con multi-tenant (correcto — solo ve los del taller actual):
Customer.objects.filter(tenant=request.tenant)
1
Frontend manda el header

X-Tenant-Id: 1 en cada petición. El frontend sabe el ID porque lo recibe al hacer login.

2
TenantMiddleware lo lee

Lee el header, busca el tenant en BD, adjunta a request.tenant.

3
Las vistas filtran por tenant

Un mecánico del Taller A nunca puede ver los datos del Taller B.

🌊 Flujo Completo de una Petición HTTP

Ejemplo real: el frontend pide la lista de clientes.

1
Frontend (React en app.autotronia.com)

fetch('https://api.autotronia.com/api/customers/', { headers: { Authorization: 'Token abc123', 'X-Tenant-Id': '1' } })

2
Nginx (sistema del VPS, puerto 443)

Recibe la petición HTTPS. Ve que el path es /api/customers/ → proxy a http://localhost:8001/api/customers/.

3
Middleware Stack (Django en contenedor 8001)

CORS ✅ → Auth (valida token, encuentra usuario Juan) → TenantMiddleware (lee X-Tenant-Id: 1, adjunta Taller Marines)

4
Router → View

config/urls.py → apps/customers/urls.py → CustomerListView

5
Service → Repository → PostgreSQL

Customer.objects.filter(tenant=1) → SQL → PostgreSQL regresa los datos.

6
Respuesta regresa

Serializer convierte a JSON → Django → Gunicorn → Nginx → HTTPS → React muestra los clientes.

🔔 Flujo Completo de una Notificación WebSocket

Ejemplo: mecánico marca una orden como "Lista". El admin lo ve en tiempo real.

1
Admin abre la app

Frontend construye wss://api.autotronia.com/ws/notifications/?token=abc123 y abre conexión WebSocket.

2
Nginx recibe el upgrade

Ve /ws/ → agrega headers Upgrade → proxy a http://localhost:8002 (Daphne).

3
asgi.py procesa la conexión

CorsOriginValidator ✅ → AuthMiddlewareStack → URLRouter → instancia NotificationConsumer.

4
Consumer.connect()

Valida token → encuentra Admin (id=5) → se une a grupos user_5 y tenant_1 en Redis → acepta → manda conteo de notificaciones.

5
La conexión queda ABIERTA

El admin navega por la app normalmente. El WebSocket sigue activo en segundo plano.

6
Mecánico marca orden como "Lista" (petición HTTP separada)

PATCH /api/workshop/orders/12/ → va por Gunicorn (puerto 8001). Django actualiza la BD.

7
Signal se dispara automáticamente

post_save en workshop/signals.py detecta el cambio → llama a notification_service.send(user_id=5, ...)

8
El servicio escribe en Redis

channel_layer.group_send("user_5", {"type": "notification_message", ...})

9
Daphne recibe de Redis

Estaba suscrito al grupo user_5. Recibe el mensaje → ejecuta notification_message(event) → lo manda por el WebSocket abierto al puerto 8002.

10
Navegador del admin recibe el mensaje

Badge se actualiza → suena el sonido → aparece el toast. Todo en menos de 100ms.

✅

Lo clave: Gunicorn (atendió al mecánico en puerto 8001) y Daphne (habla con el admin en puerto 8002) son procesos separados que se comunicaron a través de Redis. Sin Redis esto sería imposible.

¿Cuándo reiniciar qué?

Cambios en código Python (views, models, services)

En producción: docker compose up --build -d. En local: se recarga automático.

Cambios en asgi.py o consumers.py

En producción: docker compose up --build -d. En local: docker compose restart daphne

Cambios en Nginx del VPS

sudo nginx -t (verificar) → sudo nginx -s reload

Cambios en variables .env

docker compose down && docker compose up -d — los contenedores leen .env al iniciarse.
